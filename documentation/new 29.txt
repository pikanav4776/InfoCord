# InfoCord MVP Document (Privacy-Preserving Redesign)

## Author:

Pranav Madan

## Purpose:

To redefine the InfoCord MVP architecture to support **true privacy-first (end-to-end encryption)** while maintaining MVP feasibility.

---

## 1. Core Philosophy Shift

### Previous Model

* Server could read user data
* “Privacy-respecting” design

### New Model (Target)

* **End-to-End Encryption (E2EE)**
* Server stores **only encrypted data**
* **Encryption keys never leave the client**

This makes InfoCord a **privacy-preserving system**, not just privacy-friendly.

---

## 2. High-Level Architecture

### Client Responsibilities (Critical Change)

* Encrypt all note content BEFORE sending to server
* Decrypt content AFTER receiving from server
* Manage encryption keys locally

### Server Responsibilities

* Store encrypted blobs
* Authenticate users
* Handle sync and storage
* NEVER access plaintext content

---

## 3. Data Model (Updated)

### Users Table

* id (UUID, primary key)
* email (unique)
* password_hash
* created_at

### Categories Table

* id (UUID)
* user_id
* name (plaintext OK)
* color
* archived
* created_at

### Notes Table (IMPORTANT CHANGE)

* id (UUID)
* user_id
* category_id
* content_encrypted (TEXT / BYTEA)
* created_at (server timestamp)
* updated_at (server timestamp)
* archived
* version (integer for conflict handling)

---

## 4. Encryption Model

### 4.1 Encryption Strategy (MVP)

Use **symmetric encryption (AES-GCM)**:

* Each user has a **master key**
* Master key is derived from password using:

  * PBKDF2 or Argon2

### Flow:

1. User logs in
2. Client derives key from password
3. Key used to encrypt/decrypt notes locally

Server NEVER sees the key.

---

### 4.2 What Is Encrypted?

Encrypted:

* Note content

Not encrypted (MVP tradeoff):

* Category names
* Metadata (timestamps, IDs)

---

### 4.3 Key Storage

Web:

* Stored in memory only (NOT localStorage)
* Re-derived on login

Mobile:

* Stored in secure storage (Keychain / Keystore)

---

## 5. Authentication Model

* Standard login with email/password
* Server validates password hash
* Returns session (cookie-based for MVP)

IMPORTANT:

* Password is used BOTH for:

  * authentication
  * key derivation

This means:

* Password reset = data loss (MVP limitation)

---

## 6. Sync Model (Revised)

### Key Constraint

Server cannot resolve conflicts based on content.

### Strategy: Version-Based Sync

Each note has:

* version (integer)

### Update flow:

1. Client fetches note (version = 3)
2. User edits locally
3. Client sends update with version = 3
4. Server:

   * if version matches → accept, increment to 4
   * if mismatch → reject (conflict)

### Conflict Handling

Client resolves conflict:

* keep both versions
* or overwrite manually

NO last-write-wins.

---

## 7. Sync Queue (Updated)

Each operation includes:

* operation_id (UUID, idempotency key)
* type (CREATE, UPDATE, DELETE)
* entity_id
* encrypted payload
* version
* retry_count

Server must support:

* idempotency (ignore duplicate operation_id)

---

## 8. Security Model (Updated)

### Server Guarantees

* Cannot read note contents
* Cannot reconstruct user data

### Client Guarantees

* Holds encryption keys
* Responsible for data confidentiality

### Tradeoffs Introduced

* No server-side search
* Harder debugging
* Password reset limitations

---

## 9. Offline Support

Same as original plan, but:

* IndexedDB stores:

  * encrypted notes
  * sync queue

* Decryption happens only in memory

---

## 10. Technology Stack

Backend:

* Flask
* PostgreSQL

Frontend:

* HTML/CSS/JS

Encryption:

* Web Crypto API (browser)
* platform crypto APIs (mobile)

---

## 11. MVP Scope Adjustments

### Still Included

* Auth
* Categories CRUD
* Notes CRUD (encrypted)
* Basic sync

### Deferred (Even More Important Now)

* Full-text search
* Analytics
* AI features
* Password recovery

---

## 12. Critical UX Implications

You MUST communicate to users:

* “We cannot recover your data if you forget your password.”

Optional later:

* recovery key download

---

## 13. Development Phases (Updated)

### Phase 1

* Backend (same as before)
* plaintext notes initially (temporary)

### Phase 2

* Add client-side encryption layer
* migrate storage to encrypted

### Phase 3

* Version-based sync
* conflict handling

### Phase 4

* Offline + sync queue

---

## 14. What We Explicitly Avoid (MVP)

* CRDTs
* Multi-device real-time merging
* Key sharing between users
* Zero-knowledge proofs

---

## 15. Guiding Principle (Updated)

> "The server is a dumb storage layer. The client owns the data."

---

## 16. README Impact

Yes — the README MUST change.

It should now:

* Clearly state E2EE model
* Explain password = key
* Warn about data recovery limitations
* Avoid misleading claims about convenience

This is not optional — it is a **trust contract with users**.

---

## 17. Final Reality Check

This redesign makes the system:

Harder to build:

* key management
* crypto correctness
* sync complexity

But significantly stronger:

* true privacy
* real differentiation

---

## 18. Next Step

Implement in this order:

1. Normal CRUD (plaintext)
2. Add encryption layer in frontend
3. Switch DB to encrypted storage
4. Add version-based sync

Do NOT start with encryption first — integrate it after baseline works.
